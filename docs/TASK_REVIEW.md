# EvaOAuth 2.0 需求评审报告

评审日期：2026-09-18  
评审对象：`TASK.md`  
结论：**方向成立，建议有条件通过；作为产品愿景足够清晰，作为可直接执行的发布验收合同仍需补齐关键约束。**

## 1. 评审范围与证据边界

本报告评审需求的完整性、一致性、可实现性和可验证性，不执行翻新任务，不修改业务代码，也不把已有实现倒推为需求唯一正确的答案。

为判断需求是否可落地，抽查了当前 Composer 配置、统一入口、README、架构与 ADR、迁移文档、验收记录、协议测试及 CI 配置。本次执行的 `composer verify` 输出显示：

- PHP 8.5.10 下 PHPUnit 通过：122 tests、885 assertions。
- PHPStan 无错误，PHPCS 38 个文件通过。
- Composer 元数据有效，安全审计未发现已知漏洞公告。

这些结果只证明当前环境中的验证链表现；不证明干净环境安装、多 PHP 版本执行、真实 Provider 登录、发布包可用性或安全性已被完整验证。没有运行真实授权流程、触发远程 CI 或发布版本。

## 2. 值得保留的需求设计

1. **产品定位正确。** 协议层分离、应用边界统一，避免为了统一 API 扭曲 OAuth1/OAuth2 的差异（`TASK.md:7`）。
2. **允许重写但保留迁移责任。** 不要求源码兼容，却要求旧概念和常见使用方式有清晰去向，适合大版本翻新（`TASK.md:15`、`TASK.md:260`）。
3. **先研究再决定协议引擎。** 明确反对无价值的重复实现，同时要求 ADR，可以控制重写风险（`TASK.md:17`）。
4. **协议验收关注真实请求内容。** 对方法、参数、签名、刷新行为作断言，比仅验证成功响应更有效（`TASK.md:114`）。
5. **把文档作为可验证交付物。** README 示例必须执行，能够有效减少文档与 API 漂移（`TASK.md:310`）。
6. **统一工程入口。** `composer verify` 与 CI 对齐，便于陌生维护者复核（`TASK.md:224`）。

主要问题不是缺少功能数量，而是部分关键行为没有明确合同，且“功能实现”“工程通过”“真实可用”“可发布”尚未充分区分。

## 3. 优先级定义

- **P0：需求定稿前必须明确。** 否则不同实现都可能声称达标，但在安全责任、产品语义或发布结论上相互矛盾。
- **P1：2.0 发布前必须补齐。** 可以与开发并行，但不能仅靠主观判断验收。
- **P2：后续改进。** 不应借本次评审无限扩大 2.0 范围。

以下问题是需求缺口，不等于已确认代码漏洞。

## 4. 关键发现

### R1 · P0：OAuth 授权与“登录身份”的产品边界不明确

**位置：** `TASK.md:46`、`TASK.md:203`、`TASK.md:220`。

需求将 OAuth Client 的目标描述为解决 OAuth 登录问题，但没有明确身份来自 Provider 的受保护用户接口，还是包括 OpenID Connect 身份令牌验证。两者会导向不同的协议范围、验证职责和开发成本。

**建议：** 2.0 明确采用受信 Provider 用户接口归一化身份；不宣称通用 OIDC 支持，不把未经验证的 ID Token 当作身份凭据。若需要 OIDC，应另立包含签名、issuer、audience、nonce 等验证要求的范围。

**验收：** Identity 必须有非空稳定标识；姓名、邮箱、头像允许缺省；邮箱存在不等于已验证；文档明确应用负责本地账号解析、授权和账号关联。标识命名空间需说明，不能假定不同 Provider 的相同 ID 是同一个人。

当前实现已经选择 UserInfo/API 路径（`README.md:122`），说明这项决策不可避免，应提升到需求层。

### R2 · P0：状态存储只有问题，没有最低行为合同

**位置：** `TASK.md:43`、`TASK.md:173`、`TASK.md:209`。

“state 校验”不足以定义安全授权事务。需求没有规定浏览器绑定、有效期、一次性消费、多次并发登录、跨进程原子性，以及网络失败后的事务状态。

**建议：** 要求 OAuth2 事务绑定 Provider、客户端配置、redirect URI 和当前浏览器会话；OAuth1 独立保存 request token 与 secret。所有事务具备 TTL、容量上限和原子消费语义。明确默认存储与自定义适配器各自的责任。

**验收：** 覆盖过期、重放、跨会话、跨 Provider、多标签页、错误回调及消费后失败；自定义共享存储必须满足合同，而不是实现两个方法就默认安全。明确失败后重新授权，还是允许有边界的恢复。

现有架构已经规定这些行为（`docs/ARCHITECTURE.md:49`），但任务书本身不足以要求另一种实现做到同样程度。

### R3 · P0：Mock 验收与“真正可用、发布就绪”的结论之间有缺口

**位置：** `TASK.md:63`、`TASK.md:116`、`TASK.md:358`。

Mock 是协议回归测试的正确选择，但不能证明真实应用注册、Provider 参数兼容、浏览器 Cookie、反向代理或授权政策正确。最终人工验收只要求命令成功和阅读 README，仍可能放行无法完成真实登录的产品。

**建议：** 保持日常测试完全不依赖真实网站，同时把发布前的真实冒烟检查作为独立门禁，而不是加入默认测试链或要求开发网站。

**验收：** GitHub、Google、选定 OAuth1 Provider 分别记录一次真实授权与身份获取；支持刷新者记录实际刷新结果。可用临时私有测试入口，不提交凭据或要求维护公共 Demo。无法执行时标记 BLOCKED/PENDING，不推导为 PASS。

现有验收文档也明确真实 Provider 检查待完成（`docs/ACCEPTANCE.md:79`）；这是发布证据缺口，不是要求增加更多 Mock 就能解决的问题。

### R4 · P1：“安全且有用的 Debug”缺少可观察的验收目标

**位置：** `TASK.md:50`、`TASK.md:176`、`TASK.md:186`。

完全不记录数据容易满足“安全”，却未必满足“有助于排查”。反过来，原始 HTTP Trace 即使做字符串替换也难以保证安全。当前需求没有给出二者的最低交集。

**建议：** 定义白名单结构化事件，包含可信 Provider 标识、阶段、状态码、耗时、安全错误类别及非敏感关联标识。区分授权事务、令牌交换、刷新和身份读取；禁止记录凭据、原始回调、任意响应体及未经处理的异常链。

**验收：** 用几个预设失败场景证明日志能回答“哪个 Provider、哪个阶段、网络失败还是响应无效”，并验证固定结构和敏感值缺席。无需为此引入原始报文模式。

当前日志的 `operation` 固定为 `http`，无 Provider/阶段，解析失败也无独立事件（`README.md:208`）。它证明安全策略可实现，但“有用”仍缺乏足够验收依据。

### R5 · P1：支持范围与非目标不够精确

**位置：** `TASK.md:39`、`TASK.md:40`、`TASK.md:48`、`TASK.md:252`。

“现代 PHP 8.x”“OAuth1”“PSR HTTP 生态”都不是完整兼容性声明。没有最低 PHP 小版本、支持期限、PSR 接口范围、OAuth1 签名算法与请求形状、客户端认证方式等边界。

**建议：** 冻结一个支持矩阵：最低 PHP 版本、已验证版本、必要扩展、PSR-7/18 注入边界，以及是否承诺 PSR-17。明确 OAuth2 面向服务端机密客户端还是也支持公共客户端，PKCE 是否强制 S256；声明 OAuth1 支持算法及拒绝的请求形状。

**验收：** Composer 约束、CI、README 一致；新 PHP 版本在实际验证后调整支持声明。无需为了“现代”一次实现所有授权类型、签名算法或扩展标准。

当前配置限定 PHP 8.2–8.5（`composer.json:8`），这是具体设计选择，不是任务书已经确定的结论。

### R6 · P1：Provider 扩展简单，但兼容性合同仍不完整

**位置：** `TASK.md:96`、`TASK.md:106`。

endpoint、scope 和映射适合标准 Provider，但真实差异还包括 token endpoint 认证、响应编码、scope 分隔符、离线授权参数及身份字段缺省。若没有明确边界，容易逐渐变成通用参数透传或不断复制流程。

**建议：** 定义必需能力和有限的扩展点；安全关键参数不得由任意扩展覆盖。明确不支持的 Provider 特性，避免将“少量配置”理解为兼容所有服务。架构研究阶段就选定真实 OAuth1 Provider，并核实应用注册与接口可用性。

**验收：** 一个没有专用流程代码的测试 Provider，贯穿授权、回调和身份映射；另用已有 Provider 验证受支持差异。Provider 维护需记录官方接口依据及核查日期。

### R7 · P1：统一 Token 与 Identity 只有名词，缺少生命周期语义

**位置：** `TASK.md:45`、`TASK.md:46`、`TASK.md:137`、`TASK.md:201`。

需要明确 OAuth1 token secret 与 OAuth2 refresh token 的互斥关系、未知有效期与立即过期的区别、scope 的保留语义、持久化格式和跨 Provider 使用限制。

**建议：** 输出字段合同与不变量，采用不可变结果或明确更新规则；刷新返回新值，说明 refresh token 缺省时保留、返回新值时替换。库与应用分别承担哪些持久化、加密、并发刷新责任，也应写入需求。

**验收：** 覆盖过期边界、字段缺省/非法、保存恢复、刷新轮换、Provider 错配。说明客户端密钥轮换或配置变化是否导致已持久化 Token 不再可用；这是运维兼容性决策，不能只作为内部哈希实现细节。

### R8 · P1：简洁 API 没有定义部分成功与错误恢复

**位置：** `TASK.md:73`、`TASK.md:80`、`TASK.md:179`、`TASK.md:211`。

`callback()` 同时换 Token 和取用户信息很易用，但后一阶段失败时，前一阶段可能已经成功且授权码不能再使用。仅规定异常不泄露凭据，无法回答用户该如何恢复。

**建议：** 保留一站式 API，同时提供令牌交换与身份读取的可组合入口，或定义同等能力的恢复合同。错误至少区分用户拒绝/回调无效、配置问题、网络问题、Provider 响应问题与不支持操作；不要求暴露原始错误文本。

**验收：** 模拟已获取 Token 但身份读取失败；能保留凭据并单独重试安全的身份请求。不默认重试授权码交换和可能轮换 refresh token 的请求。

当前实现提供 `exchange()` 与 `user()`（`lib/OAuth.php:88`、`lib/OAuth.php:94`、`lib/OAuth.php:147`），是可采用的解决方式，不应仅停留在实现层。

### R9 · P1：PSR 可替换性未配套运输层安全责任

**位置：** `TASK.md:48`、`TASK.md:169`、`TASK.md:205`。

PSR 接口一致不代表 TLS、超时、重定向、代理和日志行为一致。若应用注入的客户端已经跟随重定向，库在返回响应后检查状态码也无法撤销已发送的凭据。

**建议：** 定义默认客户端的安全配置，要求注入客户端遵守相同约束；资源请求应有可信目标限制。明确哪些由库强制执行，哪些只能由调用方保证，不宣称一个接口就提供通用网络隔离。

**验收：** 检查默认配置与替换客户端路径；文档列出 TLS 验证、有限超时、不跟随携带凭据的重定向、不记录原始流量等条件。

### R10 · P1：验收证据类型与结论强度不匹配

**位置：** `TASK.md:314`、`TASK.md:345`、`TASK.md:354`。

允许 Test、Source、Example、Documentation 任意一种支撑 PASS，可能导致“存在 workflow 文件”被写成“CI 已通过”，或“存在 Provider 类”被写成“真实服务已验证”。这与不能只由 Agent 声明完成的目标不一致。

**建议：** 用 `需求 ID / 状态 / 证据类型 / 证据位置 / 执行环境 / 时间 / 提交标识 / 剩余限制` 记录验收。状态至少有 PASS、FAIL、PENDING、BLOCKED，不能预置全部 PASS。

**验收：** 源码只能支持结构声明；协议行为需要实际断言和执行结果；CI 需要运行记录；真实兼容性需要真实冒烟记录。需求未要求的证据不冒充强制门禁，但也不能用弱证据替代强结论。

### R11 · P1：工程门禁有入口，但质量下限和发布交付仍模糊

**位置：** `TASK.md:53`、`TASK.md:54`、`TASK.md:224`。

命令存在且退出成功，不必然说明有意义的测试、静态分析或风格检查。另一个问题是漏洞审计依赖时间和网络，不适合被描述为永久可重复的成功结论。

**建议：** 指定检查目录、静态分析起始级别和例外规则；风格检查不得默认改写代码；最低依赖与支持 PHP 矩阵应实际执行。漏洞审计联网失败应报告为未完成，而非安全通过，临时例外需有依据与期限。

**验收：** 发布候选从干净检出安装并运行统一入口；检查实际 Composer 分发包的 autoload、运行时依赖、许可证、文件包含/排除；用最小消费者项目验证安装。声明 release-ready 不等于授权自动打标签、推送或发布。

### R12 · P1：推荐阶段顺序容易造成后期返工

**位置：** `TASK.md:391`、`TASK.md:406`、`TASK.md:410`、`TASK.md:426`。

先做完协议，再统一 API，再处理 Security/Debug，容易将最影响架构的状态、错误与观测责任后置；同时要求“不加入下一阶段会推翻的临时代码”，又容易阻碍必要实验。

**建议：** 将 API 草案、安全责任和可观察性放在首个架构阶段；随后按纵向完整流程交付，而不是先横向搭建全部底层。允许有清晰目的且不进入发布包的实验，反对的是伪装成完成品的临时代码。

**验收：** 每阶段交付一个可执行路径及证据。Characterization Tests 只保留有价值的旧行为，已知不安全行为记录为刻意修正，不锁成兼容要求。

## 5. 建议补入 TASK.md 的最小要求

以下可作为一个新增的“范围与验收合同”章节，不必重写全文：

1. **产品边界：** 2.0 提供 OAuth1.0a、OAuth2 Authorization Code + S256 PKCE 和 Provider 用户接口身份归一化；不默认包含 OIDC/JWT、发现、其他 grant 或完整账号系统。
2. **兼容矩阵：** 在架构阶段确定 PHP、PSR 接口、客户端类型、OAuth1 签名算法及请求限制；约束、文档和 CI 一致。
3. **授权事务：** 浏览器绑定、Provider/配置/redirect 绑定、TTL、容量限制、原子一次消费及并发登录行为必须有合同和测试。
4. **数据合同：** Token 的协议不变量、有效期、刷新、绑定与持久化语义明确；Identity 的稳定标识和可空字段明确。
5. **错误恢复：** 一站式 callback 之外，支持 Token 已取得但身份读取失败的恢复路径；不自动重放一次性授权请求。
6. **安全责任：** 区分库、Provider、HTTP 客户端、状态存储与应用部署的保证；安全要求从首个阶段实施。
7. **可观察性：** 以安全结构化事件定位 Provider、阶段和错误类别，不以提供原始 HTTP 报文作为 Trace 达标条件。
8. **验收分层：** 本地工程、协议回归、远程矩阵、真实 Provider、分发包分别记录证据，不相互替代。
9. **发布边界：** 默认无凭据、离线 Provider 测试继续成立；真实冒烟独立执行。未经授权不发布、不推送、不操作生产账号。
10. **完成状态：** 允许明确 PENDING/BLOCKED；外部凭据、网络或 CI 权限缺失时继续完成其他工作，不伪造 PASS。

## 6. 建议执行阶段

| 阶段 | 核心产物 | 退出条件 |
| --- | --- | --- |
| A：范围与决策 | 兼容矩阵、责任边界、API 草案、引擎 ADR、OAuth1 Provider 选择 | 关键 P0 决策确定，替代方案与取舍可追溯 |
| B：工程与旧行为基线 | verify、CI、需保留的旧行为测试、迁移概念表 | 基线可复现，不把旧安全缺陷固化为要求 |
| C：OAuth2 纵向流程 | 授权事务、PKCE、Token、身份、错误与安全日志 | 一个 Provider 通过公开入口完成 Mock 全流程与失败路径 |
| D：OAuth1 纵向流程 | 独立协议模型、签名向量、真实 Provider 配置 | request token 到 authorized request 全链路内容验证 |
| E：扩展与生命周期 | Refresh、自定义 Provider、持久化合同、文档示例 | 标准扩展不复制流程，刷新与部分失败语义明确 |
| F：发布候选 | 干净安装、矩阵运行、真实冒烟、分发包、迁移与证据表 | 强制门禁均有对应实测证据，未验证项不标完成 |

安全与文档在每阶段同步完成，不单列为最后补做的包装工作。
