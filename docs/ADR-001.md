# ADR 001: Protocol engines and the EvaOAuth boundary

Status: accepted for 2.0 (2026-09-17).

## Research before implementation

The 1.x `Service` facade, separate OAuth1 `Consumer` and OAuth2 `Client`, provider endpoint definitions and normalized `StandardUser` are the enduring product design. History `af65938` introduced the facade, `8c13e1c` storage, `254399e` HMAC defaults. HEAD `36e821c` contains the 1.0.2 implementation. Legacy tests characterize alias configuration, token parsing, bearer headers and identity fields, but do not verify full OAuth1 requests. They are not modern protocol acceptance evidence.

The old implementation lacks OAuth2 state validation, PKCE and refresh exchange; OAuth1 storage is global and not consumed; randomness uses `str_shuffle`; authorized signing and Flickr mapping are incorrect; raw debug objects expose credentials. These behaviors are deliberately not compatibility requirements. The old combined result omits OAuth1 token secrets, so some persisted records cannot be migrated without reauthorization.

Reviewed standards: RFC 5849 (OAuth1 normalization and three-legged flow), RFC 6749/6750 (code, refresh, bearer), RFC 7636 (S256 and 256-bit verifier entropy), RFC 9700 (2025 security BCP). RFC 9700 takes precedence over obsolete advice in library examples: no password or implicit grants, no query bearer tokens, browser-bound one-use state, PKCE, distinct redirect URIs to prevent mix-up, TLS and no automatic credential-bearing redirects.

Reviewed PHP ecosystem: League OAuth2 stable 2.9.1 offers grant construction, PKCE and a large provider ecosystem; its developing 3.x PSR-first branch is not a stable release. League OAuth1 stable 1.11 supplies credential exchange and HMAC signing, but needs a CSPRNG override and strict response validation. Its parser/signing limitations must be constrained and regression tested rather than silently accepted. Framework integrations (e.g. Socialite) do not satisfy the framework-agnostic boundary. Maintaining two bespoke engines would duplicate mature code without product benefit.

## Decision

Use stable `league/oauth2-client` and `league/oauth1-client` behind separate engine adapters, not a home-grown protocol core and not unstable branches. Expose PSR-7 requests/responses and an injected PSR-18 transport; an internal Guzzle bridge satisfies the engines' transport APIs. HTTP redirects are not followed. Engines own grant/signature construction; EvaOAuth owns strict validation, transaction lifecycle, provider binding, identity, unified tokens, errors, and safe observability.

Application API: `new OAuth(['github' => new GitHub(...)])`, `authorize('github')`, `callback('github', $query)`, `refresh('github', $token)`, `user('github', $token)` and provider-bound PSR requests. Authorization returns a URL without issuing headers. Callback has a token-only counterpart. Provider configuration and identity mapping are distinct from protocol engines. Standard provider additions do not copy the flow.

Use PHP 8.2–8.5. State storage is browser/session-scoped, bounded, expiring and atomic-consume; PHP sessions are the default and must be started explicitly. Store redirect URI and configuration binding with each transaction. Require distinct callback URIs across configured providers. Never choose provider endpoints from callback input. Always use S256 for OAuth2. OAuth1 keeps request-token credentials, not an invented OAuth2-shaped grant.

Diagnostics are metadata-only by default: fixed event names, operation, method, status, duration and safe error category; never arbitrary bodies, headers, query strings, exception chains or provider messages. This is intentionally more conservative than denylist redaction. Applications control PSR logger policy and must not enable their transport's raw debug output.

## Consequences

A small compatibility bridge and narrow hardened engine subclasses are maintained and tested. Upstream upgrades require actual wire-request regression tests. Tokens and identities are application-boundary values, not interchangeable protocol credentials. Token persistence is explicit and application-owned; identity is fetched from trusted provider APIs, not an unvalidated ID token. No OIDC certification, discovery, JWT validation, DPoP or automatic retries are claimed.
